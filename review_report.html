视频保序输出队列竞态条件导致死锁

video/VideoProcessor.kt · processVideoFrames() · 第 166-300 行

问题：生产者-消费者-输出三协程架构使用 PriorityBlockingQueue 保序输出，但存在两个致命缺陷：

1. totalFrames 竞态：totalFrames 在生产者协程结束时才赋值（第 199 行），但 outputJob 的循环条件 while (processedCount < totalFrames || !resultQueue.isEmpty())（第 270 行）在 outputJob 启动时 totalFrames 可能仍为 0，导致循环逻辑依赖时序。

2. expectedFrameIndex 永久阻塞：若某帧在 semaphore.withPermit 块内抛异常（如 ONNX 推理失败），该帧序号不会进入 resultQueue，outputJob 的 expectedFrameIndex 永远等不到匹配，delay(1) 忙等待无限循环，协程泄漏，视频处理挂起。

影响 任何单帧推理异常都会导致整个视频处理流程永久挂起，UI 卡在"处理中"状态，需强制关闭应用。消费者异常路径未提供结果补偿。
修复建议
// 消费者异常路径必须补偿结果，保证序号连续
semaphore.withPermit {
    try {
        val detections = faceRecognizer.detectFaces(frameBitmap, detectionThreshold)
        val results = faceRecognizer.recognizeFacesParallel(frameBitmap, detections, templates, threshold)
        // ... 正常路径 offer 结果
    } catch (e: Exception) {
        // 异常时必须 offer 一个空结果，保证 expectedFrameIndex 能推进
        synchronized(resultQueue) {
            resultQueue.offer(VideoFrameResult(
                frameIndex = frameIndex,
                presentationTimeUs = timeUs,
                bitmap = frameBitmap,  // 返回原图或 null
                detections = emptyList(),
                names = emptyList()
            ))
        }
        Log.e(TAG, "帧 $frameIndex 处理失败，已补偿空结果", e)
    }
}

同时建议用 CompletableDeferred 或原子计数器替代 totalFlags 的延迟赋值，或在循环条件增加超时退出。

P0

Semaphore 并发下限保护缺失

video/VideoProcessor.kt · processVideoFrames() · 第 164 行

问题：

val semaphore = Semaphore(maxConcurrentFrames.coerceAtMost(cpuCores - 1))

当设备 cpuCores = 1（低端设备或受限模式）时，cpuCores - 1 = 0，Semaphore(0) 会导致 withPermit 永久挂起，所有消费者协程死锁，视频处理完全无法进行。即使 cpuCores = 2，Semaphore(1) 也会让并行退化为串行，但至少能跑。

影响 在单核或低核心数设备上视频处理功能完全不可用，协程永久挂起。项目宣称 minSdk 24 支持低端设备，但此 bug 让低端设备视频功能失效。
修复建议
// 确保至少 1 个许可，避免 Semaphore(0) 死锁
val effectiveConcurrency = maxConcurrentFrames.coerceIn(1, maxOf(1, cpuCores - 1))
val semaphore = Semaphore(effectiveConcurrency)

NNAPI 硬件加速伪启用（实际全程 CPU 推理）

ml/OnnxFaceRecognition.kt · initModels() · 第 211-217 行、第 233-239 行

问题：代码用 addConfigEntry("NNAPI_FLAG", "1") 试图启用 NNAPI，但这是错误的 API 用法。

addConfigEntry("NNAPI_FLAG", "1")  // ❌ ONNX Runtime 不识别此键，无任何效果
addConfigEntry("NNAPI_CPU_DISABLE", "0")
Log.i(TAG, "✅ NNAPI硬件加速已启用")  // ❌ 误导性日志，实际未启用

ONNX Runtime Android 启用 NNAPI 的正确方式是 OrtSession.SessionOptions.addNnapi() 扩展函数。addConfigEntry 只设置任意键值对，ONNX Runtime 不会识别 NNAPI_FLAG 这个自定义键。

注释和日志声称"🚀 启用NNAPI硬件加速"，README 宣传"高性能"，但实际全程 CPU 推理。骁龙 8 系列的 NPU/DSP 完全未被利用。

影响 性能损失显著。NNAPI 在支持的设备上可带来 2-5x 推理加速（NPU/DSP 卸载）。当前 README 性能数据（骁龙 8 Gen3 单帧 50ms）基于纯 CPU，启用真 NNAPI 有望降至 20-30ms。
修复建议
val sessionOptions = OrtSession.SessionOptions().apply {
    setOptimizationLevel(OrtSession.SessionOptions.OptLevel.ALL_OPT)
    setIntraOpNumThreads(optimalThreads)

    // ✅ 正确启用 NNAPI（API 8.1+）
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O_MR1) {
        try {
            addNnapi()  // 官方扩展函数
            Log.i(TAG, "✅ NNAPI 硬件加速已启用")
        } catch (e: Exception) {
            Log.w(TAG, "NNAPI 不可用，回退 CPU: ${e.message}")
        }
    }
}
注意：NNAPI 对某些算子可能不兼容，启用后需回归测试检测/识别准确率。可考虑只对识别模型（w600k_r50，计算量大）启用 NNAPI，检测模型保持 CPU。

VideoProcessor 消费者并发调用 detectFaces 违反线程安全约束

video/VideoProcessor.kt · processVideoFrames() 消费者协程 · 第 233-236 行

问题：AGENTS.md 明确声明 Session.run is NOT thread-safe。但 VideoProcessor 的多个消费者协程在 semaphore 内并发调用 faceRecognizer.detectFaces()：

// 消费者协程（最多 maxConcurrentFrames 个并发）
semaphore.withPermit {
    val detections = faceRecognizer.detectFaces(frameBitmap, detectionThreshold)  // ❌ 多协程并发调用 detSession.run()
    val results = faceRecognizer.recognizeFacesParallel(frameBitmap, detections, templates, threshold)
}

外层 semaphore permits = maxConcurrentFrames（2-4），意味着 2-4 个消费者会并发调用 detSession?.run(...)。而 recognizeFacesParallel 内部又有自己的 Semaphore(maxConcurrency=2)，两层 semaphore 嵌套，识别部分受保护，但检测部分（detectFaces）没有额外锁保护。

实际 ONNX Runtime Java API 的 OrtSession.run() 内部有同步保护，并发调用会串行化但不会崩溃——然而 AGENTS.md 的声明说明项目维护者认为它不安全。无论如何，当前并发调用不会带来检测加速（被内部锁串行化），反而增加线程切换开销。

影响 1. 若 ONNX Runtime 版本升级移除内部锁，可能导致推理结果错乱或 native 崩溃。
2. 当前并发调用被串行化，消费者并行度对检测阶段无效，实际加速仅来自对齐和模板匹配的并行。
3. 两层 Semaphore 嵌套增加死锁风险和调试难度。
修复建议

方案 A：检测和识别共享同一个 Semaphore，统一限制 ONNX 推理并发：

// 用单一 Semaphore 保护所有 ONNX 推理（detect + extract）
val inferenceSemaphore = Semaphore(maxInferenceConcurrency)
// detectFaces 和 recognizeFacesParallel 内部都用此 semaphore

方案 B：在 OnnxFaceRecognition 内部用 @Synchronized 或 Mutex 保护 detSession.run() 和 recSession.run()，让并发安全成为引擎内部契约。

ViewModel videoProcessedFrames 帧列表内存与 Compose 重组爆炸

ui/viewmodel/FaceRecognitionViewModel.kt · UiState.videoProcessedFrames · 第 73 行、第 868 行

问题：videoProcessedFrames: List<VideoFrameResult> 作为 UiState 一部分，每个 VideoFrameResult 包含 List<FaceDetection>（含 Rect + landmarks）。

// 每 5 帧更新一次，每次 toList() 复制整个列表
_uiState.update {
    it.copy(
        videoProcessedFrames = frameResults.toList(),  // ❌ 列表随帧数线性增长
        videoProgress = ...
    )
}

视频 300 帧、每帧 5 张脸时，StateFlow 持有 300 个 VideoFrameResult + 1500 个 FaceDetection 对象。每次状态更新触发 Compose 重组，需要比较整个列表（即使只看进度条），重组成本随帧数 O(n) 增长。

影响 长视频处理时内存占用持续增长，UI 卡顿，低端设备可能 OOM。Compose 重组比较深列表浪费 CPU。videoProcessedFrames 实际很少被 UI 完整使用，多数场景只需进度和最近帧预览。
修复建议

1. 将 videoProcessedFrames 从 UiState 移除，改用独立 SharedFlow<VideoFrameResult> 事件流，UI 按需收集。

2. 若需保留列表，只保留最近 N 帧（如 10 帧）作为环形缓冲：

// 环形缓冲，只保留最近 10 帧用于预览
private val recentFrames = ArrayDeque<VideoFrameResult>(10)

fun onFrameProcessed(frame: VideoFrameResult) {
    if (recentFrames.size >= 10) recentFrames.removeFirst()
    recentFrames.addLast(frame)
    // 只更新进度数字到 UiState，帧数据走 SharedFlow
}

detectFaces 生产环境过度诊断日志（每帧执行重计算）

ml/OnnxFaceRecognition.kt · detectFaces() · 第 530-555 行；preprocessDetection() · 第 1099-1104 行

问题：detectFaces 每次调用都用 Log.i 遍历前 20 个输出张量做采样：

for (i in 0 until min(outputCount, 20)) {
    val rawVal = outputs!!.get(i).value  // ❌ 触发 JNI 数据拷贝
    val flatArr = extractFlatFloatArray(rawVal)  // ❌ 递归展平，重计算
    val sample = flatArr.take(10).joinToString(...) { "%.6f".format(it) }
    Log.i(TAG, "  输出[$i]: ...")  // ❌ Log.i 级别，生产也执行
}

preprocessDetection 每次也打印前 5 像素 hex 和 float 范围。diagnosticScanOutputs 在检测为 0 时遍历所有输出做 Top-10 排序。

视频处理 100ms/帧时，这些 Log.i 刷屏且 extractFlatFloatArray 的递归展平（对 12800 元素的 score 张量）消耗可观 CPU。Logcat I 级别日志在生产环境默认输出。

影响 视频处理吞吐量下降 10-20%（诊断日志开销）。Logcat 被刷屏，影响其他日志排查。检测正常时诊断信息毫无价值。
修复建议
// 用 BuildConfig.DEBUG 包裹诊断日志，或降级为 Log.v
if (BuildConfig.DEBUG) {
    for (i in 0 until min(outputCount, 5)) {  // 减少到 5 个
        try {
            Log.v(TAG, "输出[$i]: ...")  // v 级别，默认不输出
        } catch (_: Exception) {}
    }
}

// diagnosticScanOutputs 仅在 DEBUG 模式调用
if (detections.isEmpty() && outputCount > 0 && BuildConfig.DEBUG) {
    diagnosticScanOutputs(outputs!!, outputCount)
}

视频编码器中途不 drain 输出，可能导致输入阻塞

video/VideoProcessor.kt · encodeToVideo() · 第 363-407 行

问题：drainEncoderFinal 只在所有输入帧排队后调用一次。输入循环中只 dequeueInputBuffer 和 queueInputBuffer，从不取出编码器输出。

for (frame in frames) {
    val inputIndex = encoder.dequeueInputBuffer(TIMEOUT_US)
    if (inputIndex >= 0) {
        // ... 填充数据
        encoder.queueInputBuffer(inputIndex, 0, totalSize, pts, 0)
    }
    // ❌ 从不调用 dequeueOutputBuffer，编码器输出缓冲区可能耗尽
}
// 所有帧排队后才 drain
drainEncoderFinal(encoder, muxer) { ... }

MediaCodec 编码器输入和输出缓冲区有限（通常 4-8 个）。若不中途取出输出，输出缓冲区满后 dequeueInputBuffer 会阻塞或超时返回 -1，导致帧丢失。

影响 长视频编码时部分帧因输入缓冲区获取失败被跳过（代码第 396-398 行的 else 分支提交空缓冲区），输出视频卡顿、丢帧。短视频可能无症状。
修复建议

每排队一帧就 drain 一次输出（标准 MediaCodec 模式）：

for (frame in frames) {
    val inputIndex = encoder.dequeueInputBuffer(TIMEOUT_US)
    if (inputIndex >= 0) {
        // ... 填充并 queueInputBuffer
    }
    // ✅ 每帧 drain 输出，避免输出缓冲区耗尽
    drainEncoder(encoder, muxer, false)
}
// EOS 标记后做最终 drain
drainEncoder(encoder, muxer, true)

编码器 PTS 时间戳计算错误（非单调递增）

video/VideoProcessor.kt · encodeToVideo() · 第 390-392 行

问题：

val pts = frame.presentationTimeUs.coerceAtLeast(
    (frameIdx * 1_000_000L / OUTPUT_FRAME_RATE)  // ❌ coerceAtLeast 语义错误
)

原始 frame.presentationTimeUs 按 100ms 采样间隔（FRAME_SAMPLE_INTERVAL_US = 100_000），但 OUTPUT_FRAME_RATE = 15（66.6ms/帧）。coerceAtLeast 取较大值，导致：

1. 前几帧 pts = 原始值（100000, 200000, ...），跳变。
2. 后续帧 pts 可能不单调（原始 pts 增长 100ms，计算值增长 66ms，交替取大值）。
3. 编码器要求 pts 严格单调递增，违反会导致编码失败或输出视频播放异常（花屏、跳帧）。

影响 输出视频可能在部分播放器上花屏、音画不同步或播放失败。MediaCodec 编码器对非单调 pts 行为不可预测。
修复建议
// ✅ 直接用输出帧率重算 pts，保证严格单调递增
val pts = frameIdx * 1_000_000L / OUTPUT_FRAME_RATE
encoder.queueInputBuffer(inputIndex, 0, totalSize, pts, 0)
frameIdx++

原始 presentationTimeUs 仅用于内部排序，不应直接作为编码 pts。

cosineSimilarity 重复计算已知归一化向量的范数

ml/OnnxFaceRecognition.kt · cosineSimilarity() · 第 1869-1889 行

问题：注释说"同时处理归一化和未归一化向量"，但实际两个向量都已 L2 归一化（embedding 提取后 l2Normalize，模板导入时 NpzParser.l2Normalize）。每次都算 sqrt(normA) * sqrt(normB) 是浪费。模板多时（100+ 人脸库）影响匹配性能。

val denom = sqrt(normA) * sqrt(normB)  // ❌ 已归一化，normA=normB=1
return if (denom > 0f) dotProduct / denom else 0f
修复建议
// 两侧向量已 L2 归一化，余弦相似度 = 点积
return dotProduct

若需防御性编程，可在加载时断言范数 ≈ 1，运行时直接点积。

NpzParser 解析策略过度复杂（4 种字符串策略 + raw 回退）

util/NpzParser.kt · parseNamesData() · 第 338-357 行

问题：针对 InsightFace 标准 NPZ 格式（names.npy dtype <U9 UTF-32LE），实际只需 tryParseUnicodeStrings 一种策略。但代码依次尝试 pickle、pointer、scan、null-term 四种策略 + raw float32 暴力回退，近 700 行代码。虽然鲁棒，但维护成本高，且逐行中文注释让代码更膨胀。

此外 scanReadableStrings 的 UTF-8 判断 b >= 192 不严谨（0x80-0xBF 是续接字节也会匹配），可能误判。

修复建议

保留 Unicode 策略作为主路径，其他策略降级为 DEBUG 日志的回退。若项目明确只支持 InsightFace buffalo_l 格式，可大幅精简。重构后预计 300 行以内。

AndroidManifest 缺少视频权限 + 资源管理细节

AndroidManifest.xml · 第 6-8 行；ml/OnnxFaceRecognition.kt · close()

1. 缺少 READ_MEDIA_VIDEO 权限：视频识别功能需读取视频，但 manifest 只声明 READ_MEDIA_IMAGES。Android 13+ 选择视频文件可能受限（取决于 Photo Picker 是否使用，但 SAF 选择视频仍需权限）。

<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
<!-- 缺少 READ_MEDIA_VIDEO，视频功能可能受限 -->

2. OnnxFaceRecognition.close() 无同步保护：若 close() 与 detectFaces 并发执行（如 ViewModel.onCleared 与正在进行的识别），可能 NPE。建议加 @Synchronized 或 volatile 守卫。

3. ViewModel.recycleResultBitmap() 是 dead code：定义于第 1033 行但全项目未见调用，可删除。

4. VideoProcessor.drawVideoResultsInPlace 对 hardware bitmap copy 后原图未 recycle（第 532-536 行），依赖 GC 回收，大视频时内存峰值高。

审查总结

优点

1. 核心推理实现正确：SCRFD 多步长输出解析、5 点最小二乘相似变换对齐、ArcFace 嵌入提取与 L2 归一化、余弦相似度匹配，算法实现符合 InsightFace 规范，BGR 通道顺序和归一化系数正确。

2. 注释规范执行到位：所有 Kotlin 逻辑代码逐行中文注释，符合 CLAUDE.md 要求，变量用途、函数目的、异常边界标注清晰。

3. 并发设计有想法：channelFlow 生产者-消费者模式、PriorityBlockingQueue 保序输出、动态并发度调优，思路正确，只是实现有竞态 bug。

4. 资源释放基本到位：ONNX Session/Tensor、MediaCodec、MediaMuxer、Bitmap 都有 try-finally 或 close() 保护。

主要风险

1. 视频处理流水线稳定性：P0-1 的队列死锁 + P0-2 的 Semaphore 下限缺失 + P1-5/P1-6 的编码器问题，让视频功能在生产环境可靠性存疑。建议优先修复 P0 后做完整视频回归测试。

2. NNAPI 伪启用是性能损失：项目宣传"高性能"但实际未用硬件加速。修复 P1-1 后建议重新 benchmark，更新 README 性能数据。

3. 生产日志过多：P1-4 的诊断日志在 release 包仍执行，影响视频吞吐和电池。建议引入 BuildConfig.DEBUG 开关。

建议修复优先级

1. 立即修复（P0）：VideoProcessor 队列死锁补偿 + Semaphore 下限保护。
2. 本周修复（P1 核心）：NNAPI 正确启用、编码器 drain + PTS、ViewModel 帧列表改造。
3. 迭代优化（P1 其余 + P2）：诊断日志开关、模板过滤缓存、构建配置清理、权限补全。
